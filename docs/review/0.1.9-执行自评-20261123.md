## 四、审核中发现的真实功能缺口（已补，非走过场）

首轮自审对照已批准设计文档时，发现两处「文档写了、代码没做」：

### 缺口 A：客户端从不轮询待跳转队列 → 升级后不会跳到新会话

- 设计 §5.3 / §7 R3-1 要求：node 半边写入待跳转队列 → client 半边每 1s 拉 `GET /pending-navigation` → `ctx.uiWorkspace.openSession(id)`。
- 实测：`src/index.ts` 有队列(:281)、有写入(:1643)、有路由(:2399)，但 `src/client/index.ts` 里 grep `pending-navigation|pendingNavigation|openSession` **零命中** → 功能实际从未生效。
- 修法：client 新增 `NAV_POLL_MS = 1_000`(:66)、`navigationInFlight`(:297)、`loadPendingNavigation()`(:302)、apply 内 `setInterval`(:3866)。
- **修法中的一次自我审查（重要）**：服务端是「取走即清空」语义。若 `uiWorkspace` 服务还没起来就先 fetch，目标会被清掉又跳不过去 = **永久丢失**。故实现刻意做成**先确认服务在位再去拉**（`clientCtx.get('uiWorkspace')` 缺失 → beacon `navigation-wait` 并 `return`，**不 fetch**），并有专门用例守住（`0.1.9 缺口A：宿主没有 uiWorkspace 时不拉队列`）。

### 缺口 B：新建子会话未 attach 到 workspace → 用户侧边栏看不到新会话

- 研究文档 :109/:152/:250 与宿主 controller 的 fork 配方（`dsh-api-session-controller/src/commands.ts:301-311`）都要求 `workspace.attachSession(childId)`；本地 `dsh-session-escalation/lib/index.js:414-421` 同样做。
- 实测：`doEscalateSession` 里 `create.call(agentsSvc, ...)` 之后没有 attachSession → 子会话不在任何 workspace 的会话列表。
- 修法：`src/index.ts:1572-1573` 按宿主配方实现 —— `workspaceRegistry.list()` → 找 `sessionIds.includes(parentSessionId)` → `await workspace.attachSession(childId)`；失败只记 `escalate-attach-failed` 日志，**不阻断升级**（分支已建好，回滚代价更大）。

## 七、边界与安全

- **两个新能力默认关闭**：`src/core.ts:174` `autoResumeEnabled: false`、`src/core.ts:178` `escalateEnabled: false`。默认安装不产生任何自动续作或自动建会话行为。
- **副作用已在 UI 明示**：双能力区每个区块都有说明（「会真实投递消息、消耗上游额度，默认关闭。」「会中断旧会话正在跑的回合，默认关闭。」）。
- **能力 2 的破坏性**：会建新会话、投递交接消息、并对父会话调 `archiveSession(parentSessionId, { stopActivity: true })`（宿主原生可逆，会中断父会话运行中的 turn）。仅本插件自己发起的升级才归档（`entry.escalatedTo !== null` 直接 return，:1663-1665）。
- **凭据零落盘**：本版无任何凭据读写；无新增网络依赖；无新增第三方依赖。
- **fail-closed 覆盖**：占用数据缺失 → 零动作；`escalateEnabled` 关 → 零动作；回合未完成 / 会话繁忙 / 链深触顶 / 预算触顶 → 零动作；`workspaceRegistry` 缺席 → 不归档（记 `escalate-archive-unavailable`）；`agentPresets` 解析失败 → 用宿主默认 preset。
